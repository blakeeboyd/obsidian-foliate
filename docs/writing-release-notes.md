# Writing release notes and docs

How Foliate's user-facing text is written: changelog entries, GitHub release
bodies, the README, and in-app copy. The changelog is the source corpus — the
release body is generated from it, so getting the changelog right gets both.

## The rule

**Lead with what the user sees.** A person reading these notes wants to know
what changed for them, not how the code changed. Open every entry on the visible
effect.

Three moves carry it:

1. **Bug fix: name the recognizable symptom first.** The reader recognizes the
   entry by the thing that was broken for them, not by the fault in the code.
   "Typing a markdown link froze the editor" — then, if it helps, the cause.
2. **Mechanism only where it changes what the user should do.** Include how it
   works when the reader acts on it (a setting to flip, a migration that runs, a
   limitation to plan around). Cut it when it is only how you happened to fix it.
3. **Cut internal implementation vocabulary.** Function names, event names, file
   paths, class names, regex, the word "race" — none of it means anything to a
   reader who never sees the source. If a sentence only parses with the code
   open, rewrite it.

## Worked examples

From this repo's `CHANGELOG.md`. Before/after is in git history.

**Bug fix — symptom first, mechanism dropped:**

> Before: "Auto-move fired a second `renameFile` inside the vault `rename`
> event, racing Obsidian's own link-rewrite pass, so links broke on rename."
>
> After: "Renaming a taxa file no longer breaks the links pointing to it, at any
> batch size."

The symptom ("renaming broke links") is what the user recognizes. "at any batch
size" stays because it tells them the fix holds for the large renames that
triggered it. The rename-event mechanism is gone — it changes nothing they do.

**Feature — mechanism kept, because the user acts on it:**

> "Context-aware mentions (experimental, off by default). If a taxa file's alias
> is a common word … it can flood every note with unlinked mentions. With this
> on, that alias only surfaces … in notes that also mention one of the file's
> related terms. Enable it under Settings → Experimental → Context-aware
> mentions, then set files up from a sidebar item's action…"

The "how" survives here because the reader has to do it: find the setting, turn
it on, configure files. That is user-facing mechanism, not implementation.

## Document-type notes

- **Changelog** (`CHANGELOG.md`) — the canonical text. Keep a Changelog format:
  `### Added` / `### Changed` / `### Fixed` under each `## x.y.z - DATE`. Write
  entries as complete sentences, not commit subjects. This is where the rule
  lives; the rest inherit it.
- **GitHub release body** — auto-generated by `release.yml` from the matching
  CHANGELOG section, minus the `## x.y.z - DATE` heading (GitHub already shows
  title and date). Do not hand-write it; fix the CHANGELOG and the release
  follows.
- **README** — same voice, describing current behavior rather than a change.
  Lead with what the feature does for the user; keep setup steps concrete.
- **In-app copy** (settings labels, command names, notices) — shortest form of
  the same rule. Name the effect, not the internal toggle. A command is what it
  does for the user ("Copy debug report to clipboard"), not what it calls.

## Voice

Follow the vault writing voice (banned em dashes, no signposting, no purpose
stingers, plain words over AI-marker vocabulary). One product-specific carve-out:

- **Keep literal UI glyphs verbatim.** When an entry names a character the user
  sees in the interface (the ✕ clear button), that glyph is a UI reference, not
  decoration. An editing pass that swaps Unicode for ASCII must leave these
  alone.
